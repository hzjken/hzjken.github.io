01 · The basicsWhat is Pi Agent?

Most AI coding agents these days are opinionated. They ship with built-in sub-agents, plan modes, permission popups, background processes, and a fixed idea of how you should work. You adapt to them.

Pi Agent flips that. It's a minimal, terminal-based coding agent — a harness that hands an LLM exactly four tools to touch your filesystem and shell, and otherwise gets out of the way. It was built by Mario Zechner (known online as badlogic), it's MIT-licensed and written in TypeScript, and it's the engine underneath OpenClaw — one of the most popular open coding agents right now. Its tagline says it plainly: "there are many agent harnesses, but this one is yours."

There's a fun detail about the name. Mario called it "Pi" precisely because it's almost impossible to Google — as he put it, he wanted "a name that's entirely un-Googleable, so there will never be any users." The joke, of course, is that it became popular anyway, and it now pulls millions of weekly npm downloads.

But here's the thing that actually makes Pi interesting: it isn't impressive because of what it has. It's interesting because of what it deliberately leaves out — and how well that tiny thing still works. So let's dig into the harness itself.

02 · The splitTwo camps of agent harnesses

Step back and the coding-agent world sorts into two camps, and they could not disagree more on the core question: how much should the harness do?

One camp is maximalist. Claude Code is the clearest example — dozens of built-in tools, a system prompt tens of thousands of tokens long, native sub-agents, plan mode, a multi-layer permission engine, MCP baked in. The harness does almost everything, so the model and the user don't have to. It's a spaceship: powerful, polished, and very much an opinionated product.

The other camp is minimalist, and that's Pi. Four tools. A system prompt under a thousand tokens. No built-in MCP, no sub-agents, no plan mode, no sandbox. The harness does as little as it can get away with — just enough to run the loop — and pushes every "feature" out to extensions.

My take: Pi's minimalism isn't a limitation dressed up as a virtue. It's a deliberate abstraction boundary, and that boundary is exactly why Pi gets reused in places a maximalist harness can't reach. Cloudflare, Flue (from the Astro team), and Agno all build on Pi's core. As one write-up put it: a harness that tries to do everything — MCP, sub-agents, plan mode, sandboxing — can't slot cleanly into a platform that already provides those things natively. "Just the loop" turns out to be the right cut.

Mario's motivation is worth quoting directly, because it explains the whole philosophy. He'd been a Claude Code daily driver, but over time it "turned into a spaceship with 80% of functionality I have no use for" — every release changed the system prompt, broke his workflows, and shifted model behaviour. Pi is his answer: a stable, predictable, deeply understandable agent that does one thing well. Source.

03 · What's insideThe four packages

Pi isn't a monolith — it's a stack of four npm packages, each owning one concern. They're published under the @earendil-works scope (moved from @mariozechner in May 2026), and they layer cleanly: the bottom talks to LLMs, the middle runs the agent loop, and the top two give it a face and wire it into a CLI.

04 · How it worksThe loop, the events, the hooks

Strip the UI and the providers away and you're left with pi-agent-core — the harness. It does exactly five things: hold stateful context across turns, execute tool calls the model returns, stream structured events for every step, queue and steer the model when it tries to do too much at once, and expose two hook points to intercept every tool call. That's the whole engine.

The for await event stream is the single most important design choice in Pi. Because the harness speaks in events rather than returning one big result, anything can sit on the other end: the terminal UI, a print-mode script, an RPC bridge into an IDE, or — crucially — a whole framework. Flue wraps that stream into HTTP and WebSockets; Agno maps it into a Python runtime; Cloudflare pipes it through Durable Objects so an agent can crash and resume. The harness doesn't know or care. That decoupling is what "just the loop" buys you.

05 · Four tools, that's itread, write, edit, bash

The entire built-in toolset is four verbs. read a file, write a file, edit a file, run bash. No glob, no grep, no web search, no sub-agent spawner — those exist, but as extensions you add when you need them, not as permanent fixtures in the prompt.

That's the whole runtime. It sounds spare to the point of awkward — no grep? no glob? — until you remember that bash already is grep, glob, git, npm, curl, and anything else on your machine. The model just calls them through one tool instead of twenty. What you lose is the polished per-tool UX (a dedicated grep tool can render matches nicer); what you gain is a prompt that stays tiny and a toolset the model fully understands.

06 · The leverageWhy so little does so much

This is the real question. Four tools and a sub-1000-token system prompt sounds like a toy — yet Pi is the engine under OpenClaw and a daily driver for a lot of serious engineers. How does so little do so much? A few reasons, and they compound.

Four tools are the universal primitives

Coding is, at bottom, three actions: see code, change code, run code. read, write/edit, and bash map onto those almost perfectly. A specialised tool — a grep tool, a git-blame tool, a web-search tool — is usually just bash with nicer formatting. By keeping the core to the primitives, Pi keeps the model's choice set small and unambiguous, and keeps the tool descriptions out of the prompt until they're actually needed.

A short prompt is a stable prompt

Pi's system prompt is under a thousand tokens. Claude Code's is on the order of 55,000. That gap isn't just cost — it's behaviour. A giant, shifting system prompt is exactly what broke Mario's Claude Code workflows: every release changed what the model saw, so the model behaved differently. A tiny prompt that barely changes is a predictable prompt. You can actually hold the whole thing in your head, reason about why the model did what it did, and trust it'll do the same thing tomorrow.

Pi keeps the prompt lean by not stuffing it with tool docs and procedures — it loads those on demand via AGENTS.md and skills.

Exact-text edit removes a whole failure mode

Fuzzy or line-number-based patching is where a lot of agents quietly corrupt files — they guess the region, the model's line count is off by one, and the edit lands in the wrong spot. Pi sidesteps this entirely: the model quotes the exact old text, the harness finds that exact string, done. The failure mode simply doesn't exist. That single decision does more for reliability than a dozen fancier tools would.

The event stream decouples the harness from the host

Because pi-agent-core speaks in a for await stream of events rather than owning the UI, it can be embedded anywhere without modification — Node, Cloudflare Workers, Deno, Bun, or a Python bridge. A maximalist harness that bundles its own UI, permissions, and sandbox can't be slotted into a platform that already provides those. Pi can, because it doesn't. The minimalism is the portability.

The agent extends itself

This is Pi's signature trick. Need a new tool? You don't edit a config file and restart — you ask Pi to write the extension with its own write tool, run /reload, and the new capability is live. Plan mode, sub-agents, a permission gate, even a custom compaction strategy — features other harnesses hardcode into the core are just extensions here, and the agent can author them at runtime. Extensibility is a runtime primitive, not a build-time feature.

The same power cuts both ways — see the limits section. An extension that can write the next tool can also write a careless one, and extensions run with your full permissions. That's why Pi leans on community packages like permission-gate and isolation layers like Gondolin (a tiny Linux VM) rather than pretending the core should police itself.

Tree-branch sessions keep exploration free

Pi's sessions aren't linear — they're trees. You can jump back to any earlier turn and branch down a different path, and every branch lives in one JSONL file. This matters for token economy: you don't have to keep alternative approaches in context (which would bloat the prompt) — you keep them as sibling branches and switch between them. Exploration becomes nearly free.

07 · Keeping the prompt shortContext engineering

So how does Pi stay under a thousand tokens of system prompt while still knowing your project's conventions? By loading context instead of baking it in. A few levers do the work:

  • AGENTS.md — write your conventions, common commands, and safety rules in an AGENTS.md at the project root (and a global one in ~/.pi/). Pi walks up from your working directory, loads every one it finds, and concatenates them. The model knows your team's standards before you type a word. (It reads CLAUDE.md too, so dropping Pi into a Claude Code project just works.)
  • SYSTEM.md overrides — per-project instructions that override the global ones when you need something more specific.
  • Compaction — as a session grows, older turns get summarised so the working context stays focused. You can even swap in your own compaction strategy as an extension.
  • Skills — self-contained capability packs loaded on demand. Pi follows the Agent Skills standard, so skills written for Claude Code or OpenAI Codex work here too. Only the short description stays in context; the full instructions load when a task matches — progressive disclosure.
  • Prompt templates — Markdown files in ~/.pi/agent/prompts/ become slash commands. Type /review and it expands into your full review checklist.

And Pi runs in four shapes beyond the interactive terminal: print mode (-p) for one-shot scripts and CI, JSON mode that streams structured events, RPC mode that speaks strict JSONL over stdin/stdout so a non-Node process can drive it, and an SDK for embedding agent sessions directly in an app. Same harness, four deployment surfaces.

One more contrast worth naming: their loops. Claude Code's is a 12-step state machine — budget trimming, micro-compaction, context collapse, auto-compaction, streaming tool execution, stop-hook evaluation, and more, every single cycle. Pi's is, charitably, five things. Claude Code's complexity exists for good reasons (keeping a 55k-token context usable takes real engineering), but it's complexity you can't inspect or bypass. Pi's loop is small enough to read and reason about. There's a direct line from "small loop" to "stable, predictable behaviour" — which was the whole point.

09 · The honest limitsWhere Pi breaks

I've been fairly glowing, so let me be blunt about the trade-offs, because they're real.

It runs with your full permissions. Out of the box, Pi has your file, process, and network access — so rm -rf or reading your .env is very much possible. The core doesn't sandbox itself; it expects you to add isolation: Gondolin (a tiny Linux VM that intercepts every file/command op), a Docker container, or OpenShell for fine-grained permission control. Community packages like permission-gate and zeroAccessPaths cover the common gaps. None of this is automatic.

No native MCP. If your workflow depends on the Model Context Protocol, you add it as an extension — community packages exist for common servers. That's fine, but it's an assembly step Claude Code doesn't make you do.

Production safety is on you. The 3-layer permission engine and real-time risk assessment that Claude Code ships? You're building the Pi equivalent yourself, or pulling community packages and trusting their source. For a solo dev that's a fair trade; for an enterprise rollout it's real work.

"The agent extends itself" is also a footgun. An extension that can author the next tool has your full permissions, and a misbehaving or malicious one can do real damage. Review any third-party Pi package's source before you install it — the power cuts both ways.

So when do you reach for the maximalist camp instead? When you want batteries-included safety and polish with zero assembly, when you're happy to live inside Anthropic's ecosystem, and when you don't need to embed the agent inside another platform. If any of those is false — you're building your own agent product, you need model portability, or you want the agent to run on the edge — Pi's trade starts to look a lot better.

The deeper lesson, for me, isn't "minimal beats maximal" or the reverse. It's that the real question is where you draw the abstraction boundary. Claude Code draws it wide — the harness owns tools, permissions, orchestration, the works — and you get a powerful, safe, opinionated product. Pi draws it tight — the harness owns only the loop — and you get something small enough to embed anywhere, extend at runtime, and fully understand. A harness that tries to do everything can't slot into a platform that already provides those things natively; a harness that's just the loop can go anywhere.

Pi's bet is that the loop is the part worth keeping, and almost everything else is better pushed to the edge. For a lot of us — especially anyone building on top of an agent rather than just using one — that bet pays off.
