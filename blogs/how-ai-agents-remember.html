01 · The basicsWhat is agent memory?

Every time you start a new session with an AI agent, it wakes up with perfect amnesia. It doesn't know you, it doesn't know your project, and it has no idea what the two of you did together yesterday. The model's weights are frozen — nothing from your conversations ever gets "learned" into them.

Agent memory is everything the harness does to fight that amnesia. It's the set of mechanisms that carry information beyond the current context window: what gets written down, where it's stored, and how it finds its way back into the model's view at the right moment.

Say you're building Nimbus, a little cloud-cost dashboard, with an agent helping you over several weeks. On Monday you decide to deploy to Fly.io instead of Vercel. On Wednesday you try Redis caching and roll it back. If the agent remembers those two facts next week, it feels like a colleague. If it doesn't, you're re-explaining your stack every single morning — and it might cheerfully suggest Vercel again.

So memory is really the difference between an assistant and a goldfish. But why has it become the hot design problem in agent tooling right now?

02 · Why it mattersMemory is what compounds

A coding agent without memory is still useful — the models are that good. But it can't compound. Every session starts from zero: same conventions re-explained, same mistakes repeated, same decisions re-litigated. With memory, each session builds on the last. The agent learns that you prefer pnpm, that the Nimbus deploy script is fragile, that last Tuesday's Redis experiment failed — and it gets a little more useful every day you use it. That's why every serious agent harness now ships a memory story.

The field borrowed its vocabulary from cognitive psychology, mostly via the CoALA paper (Cognitive Architectures for Language Agents). Four types of memory, and each maps to something concrete that harnesses actually build:

Working memory

The context window itself

This conversation, right now — prompts, tool calls, results. Fast, but volatile and size-capped.

"We're debugging the Nimbus deploy script…"
→ managed in-session, via compaction
Semantic memory

Facts about you & the world

Durable knowledge: preferences, conventions, project facts.

"Nimbus deploys to Fly.io · user prefers pnpm"
→ lives in MEMORY.md files & user profiles
Episodic memory

Records of past events

What happened, when, and how it went — past sessions and experiments.

"Jul 14: tried Redis caching, rolled it back"
→ lives in daily logs & searchable session history
Procedural memory

Skills & how-to

How to do things — mostly baked into weights, the system prompt, and tools.

"how to run the Nimbus deploy"
→ mostly fixed; skills files are the writable slice

Working memory is the easy half — every harness handles it somehow. The interesting fight is over long-term memory (the semantic and episodic kinds), and it comes down to two questions: where does it live? and who writes it?

Looking across the harnesses I use or follow — Claude Code, OpenClaw, WorkBuddy, Hermes Agent, and Pi — the answers to "where" fall into three camps.

Camp A — memory is the context window: keep everything in the conversation, and when it fills up, summarize.

Camp B — memory is files: write it down in markdown, and inject those files into every session.

Camp C — memory is a searchable store: index everything, retrieve only what's relevant, when it's relevant.

Let's walk through them in order — it's also roughly the order the field evolved in.

Camp A
Memory is the context window

Keep everything, then compact

The simplest possible memory strategy: don't build one. The conversation is the memory — every prompt, tool call, and result stays in the context window, so within a session the agent recalls everything perfectly. The problem only shows up when the window fills. And it always fills: a long debugging session with big tool outputs can burn through 200k tokens fast.

That's where compaction comes in — the one memory mechanism every single harness ships. When the window gets close to full, an LLM summarizes the older turns into a compact brief, and the conversation continues with the summary plus the most recent turns. Here's the flow:

The purest expression of this camp is Pi, Mario Zechner's minimalist terminal agent. Pi has no cross-session memory at all — no memory files, no memory tool, no user profile. Its stance: project conventions belong in a hand-written AGENTS.md in the repo, in-session continuity belongs to its (genuinely excellent) compaction, and nothing else is needed. Sessions are inspectable JSONL files you can resume or branch.

The appeal of Camp A is real: zero infrastructure, nothing to maintain, nothing to go stale. Within a session it works great. The limits are just as real: compaction is lossy, and the moment you close the session, everything dies with it. There's no compounding — tomorrow, the agent is a stranger again. Which is exactly the gap the next camp set out to fix.

Camp B
Memory is files

Write it down, load it every session

The core idea of Camp B: if something is worth remembering, write it into a markdown file, and make sure the agent reads that file at the start of every session. No databases, no embeddings — just text files on disk that you can read, grep, diff, and commit to git. The model only remembers what someone bothered to write down.

The most influential design here is Claude Code's CLAUDE.md hierarchy — four layers of memory files, from company-wide down to just-you:

Claude Code popularized the pattern, but every harness has its own file layout, and the differences are telling:

Hermes Agent

~/.hermes/memories — the extreme diet
MEMORY.md # 2,200 chars max
USER.md # 1,375 chars max

fill % shown in the prompt

The minimalist outlier: two tiny hard-capped files, frozen into the system prompt as a snapshot at session start (keeps prefix caching intact). When they're full, writes fail — and the agent must consolidate old entries to make room.

The strengths of files are why this camp won the mainstream: total transparency (you can read exactly what your agent believes), portability (commit CLAUDE.md to the repo and the whole team shares it), and zero infrastructure. The weaknesses are just as instructive. Every always-loaded file is a standing token tax on every turn — Claude Code's own docs recommend keeping CLAUDE.md under ~200 lines, and ship a /doctor command to propose trims. Files also go stale: the note saying "deploys to Vercel" doesn't delete itself when you switch to Fly.io. And the whole approach hangs on discipline — if the agent forgets to write something down, that knowledge silently dies at the end of the session. No error, no warning.

Which raises the obvious question: what if, instead of injecting a curated few files into every session, you kept everything — and fetched only what's relevant, when it's relevant?

Camp C
Memory is a searchable store

Index everything, retrieve on demand

Camp C treats memory less like a notebook and more like a search engine. Every daily log, every past session, every note gets indexed — by meaning and by keyword — and at query time the agent (or the harness) pulls back just the few entries that matter. Nothing sits in the context window permanently, so the store can grow to months of history without any per-turn tax.

Hermes Agent takes a deliberately different bet within the same camp: its session_search runs plain full-text search (SQLite FTS5) over every past session and returns raw, unmodified messages — no LLM summarization, no truncation. The reasoning: a summary is someone else's opinion of what mattered; verbatim history lets the current agent judge for itself. WorkBuddy's conversation_search plays a similar role for past sessions, sitting next to its file layers.

And if you don't want to build the store yourself, there's a whole plug-in ecosystem: Mem0 runs an extraction pipeline that distills each conversation into deduplicated fact records; Zep/Graphiti keeps a temporal knowledge graph that tracks when each fact became true and when it stopped being true — a direct attack on the stale-memory problem.

The camp's strengths: it scales (months of history, constant per-turn cost) and it's automatic — no curation chore. The weaknesses: retrieval is probabilistic, so it can miss the note you needed or surface a confidently irrelevant one (similarity ≠ relevance); the index goes stale along with the notes; and the store is opaque — most users never inspect what their agent has on file. It's also the camp with real infrastructure: embeddings, an index, a ranking pipeline.

Notice, though, that all three camps quietly dodged the second question — who actually writes the memory? That turns out to matter just as much as where it lives.

06 · The other axisWho writes the memory?

Storage is only half the design. Every harness also picks a write path — and there are three, with a real trade-off between effort and trust:

You write it

Hand-edit the files, or use shortcuts like Claude Code's # prefix to append a note on the fly. You decide exactly what the agent believes.

// reliable & precise — but it's a chore, and you'll forget

The agent writes it

The agent curates its own memory through tools — Hermes' add / replace / remove, Claude Code's auto-memory, OpenClaw's pre-compaction "flush" turn and dreaming sweep. The lineage goes back to MemGPT's self-editing memory blocks.

// scales with the work — but it can save junk, or forget to save

A pipeline extracts it

A background process distills each conversation into fact records automatically — ChatGPT's memory and Mem0 work this way. Zero effort, zero control.

// effortless — but opaque: it decides what you "meant"

The trend is clearly toward the middle path — agent-curated memory with human audit. The files stay human-readable (so you can always check its work), but the agent does the janitorial labor. Hermes is the most honest about the cost: it scans memory writes for prompt-injection and forces the agent to consolidate when full — memory management becomes part of the agent's job, not yours.

07 · The fine printWhere agent memory breaks

Before you get too excited about an agent that remembers everything — memory introduces its own failure modes, and a few of them are nasty. These are the four I'd actually worry about:

Memory poisoning

If an attacker can slip text into what your agent reads (a web page, a repo, an email), they can get malicious instructions persisted into memory — a stored prompt-injection that fires in every future session. The MINJA attack showed it works with queries alone.

// the nightmare scenario for always-on memory

Stale & contradictory

Notes don't expire on their own. "Deploys to Vercel" sits next to "deploys to Fly.io," and which one the agent believes is a coin flip. Zep's whole temporal-graph design exists mostly because of this.

// silent, common, and hard to notice

Junk retrieval

Search-based memory fetches by similarity, and similarity isn't relevance. The more history you index, the more confidently-wrong snippets land in context and quietly steer the answer off course.

// more stored → more noise fetched

Context rot

Even inside the window, more isn't better: models attend less to the middle of long inputs (lost-in-the-middle) and degrade as inputs grow (Chroma's context-rot report). Stuffing every memory file into every prompt can make the agent worse.

// more context ≠ more memory

A fairness note on OpenClaw: its maximalist "remember everything, run everywhere" design also had a rough security stretch in early 2026 — a string of high-severity CVEs, including an RCE. That's not a coincidence: the more an agent persists and the more autonomy it has, the bigger the blast radius when something slips through. Memory and security are the same conversation.

08 · Wrapping upSo whose memory is best?

Here's the cheat sheet — the five harnesses, ranked by real-world adoption, with the camp(s) each one bets on:

My read — and I'll flag this as a personal take, the field hasn't settled it: the camps are converging, not competing. The design that keeps winning looks like a hybrid: files for identity and curated facts (small, always loaded, human-audited), search for deep history (everything else, fetched on demand), compaction for the working session, and the agent itself doing the writing while you do the auditing. Claude Code, OpenClaw, and WorkBuddy are all drifting toward exactly that shape from different directions.

Because here's the thing: the models are all renting roughly the same brain. Memory is the part that makes it yours.
